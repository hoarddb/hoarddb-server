# ringseed: the social data set, in the entity-centric shape

`ringseed` loads the S-10k (or S-100k) social data set into a running `hoarddb-server` so you can log
in and browse it. It talks the entry-ring wire protocol through the `github.com/hoarddb/hoarddb-server/ringclient` package.

Unlike the legacy seeder (`../engine_hoard_seed.go`, one bucket per user under the `h1`/`h64`/`hu`
placements), this one never creates a bucket per user. A user is a **document** in one `User`
bucket, and the user's own collections are **store fields of that document** (the data-lives-with-its-entity rule):

    create bucket User { Name string, Bio string, Joined datetime, FollowerCount int, FollowingCount int,
        Avatar binary, Photo binary, Posts btreeStore, Feed lifoStore, Following hashStore, Followers hashStore, Inbox fifoStore };
    create bucket Post { Author string, Seq int, Text string, Created datetime, Tags array, ReplyTo string,
        Likes hashStore, Comments fifoStore };

Two buckets, whatever the data set size. `Post` exists because a post has a like set and a comment
thread of its own, and a store field lives on a document; the author's `Posts` store holds only a
reference (`post: "<author>:<seq>"`), keyed so the newest sorts first. The legacy `Media` blobStore
(avatars, photos) becomes the two `binary` scalar fields `Avatar` and `Photo` of the users that own one:
the ring wire has no verb that writes a blobStore yet. A follow edge in `Following` and `Followers`
carries the other user's id (`user`) because a store list returns elements without their keys.

The seeding code lives in the `ringload` package next to this command (`../ringload`), which the
harness' `-engine ring` also calls; this directory is only the flags.

## Start a server, seed, look

1. Start a server on a scratch directory. It prints the address it listens on for drivers and its
   certificate fingerprint:

        HOARDDB_DATA_DIR=<scratch dir> HOARDDB_ROOT_USER=admin HOARDDB_ROOT_PASSWORD=<12+ characters> hoarddb-server

2. Seed it (from `github.com/hoarddb/hoarddb-server/`). `-insecure` skips the certificate check and is for a server you started
   yourself on this machine; otherwise pass `-fingerprint <value the server printed>`:

        HOARDDB_ROOT_PASSWORD=<same password> go run ./bench/social/ringseed -addr <host:port> -insecure

   Flags: `-addr` (env `HOARDDB_ADDR`), `-user` (env `HOARDDB_ROOT_USER`, default `admin`), `-password`
   (env `HOARDDB_ROOT_PASSWORD`), `-insecure` or `-fingerprint`, `-dataset S-10k|S-100k`, `-database`
   (default `social`), `-workers` (default 32), `-connections` (default 4).

3. Expect progress lines every two seconds, then one JSON line on stdout:

        {"database":"social","dataset":"S-10k","users":10000,"posts":100000,"buckets":2,"writes":1010000,"seed_s":23.3}

   S-10k is about 1.01 million writes. Measured on a 4-vCPU-class laptop-sized VM, server and seeder on the
   same machine, default settings: 23.6 s and 498 MB of data directory. S-100k is ten times that.

Seeding is **not** resumable. Running it again against a database that exists is refused, with the
way out in the message: seed a fresh database with `-database <name>`, or start the server on an empty
data directory.

## What is in it

The data is generated by a copy of the harness generator (`../ringload/graph.go`, `words.go`), seeded with the
harness constant, so a user, post, follow edge, feed entry, like and comment are the same as the legacy
seeder's. `TestGeneratorMatchesTheHarness` in `../ringload` and `TestRingSeedParity` in `..` pin the same
figures (`TestMediaMatchesTheHarness` and `TestRingSeedMediaParity` pin the avatar and photo bytes) and fail if either copy drifts. Every user has about 10 posts, 20 follows, a feed of up to 20
posts (copies, newest on top), and 5 notifications. User ids are `0`..`9999` as text; post ids are
`<author>:<seq>`.

## Cost per entity (rule 11)

Declared shape only, before any element: a `User` document costs its header (about 128 B resident) plus
its scalar fields (name, bio, joined and two counts, about 300 B) plus about 125 B for each of its 5
store fields: roughly 1.05 KB per user. A `Post` document is the same header plus about 450 B of
scalars plus 2 store fields (250 B). Elements (posts index, feed, follows, inbox, likes, comments) are
data and cost their own bytes. No bucket, file descriptor, goroutine or metric is added per user or
per post; a membership change stays O(1) in the number of buckets (2).
